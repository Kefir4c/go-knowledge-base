## 🟢 БЛОК 1. ТИПЫ ДАННЫХ (спрашивают ВСЕГДА)
### 1.1. Строки (String)
**Логика:** Строки — самый простой тип, хранят бинарные данные (сериализованные объекты, текст, числа). Используются для кэширования, счётчиков, временных данных.  
**Что учить:** SET, GET, DEL, EXISTS, EXPIRE, TTL, INCR, DECR, APPEND, STRLEN.  
**Связь с Go:** В go-redis — `client.Set()`, `client.Get()`, `client.Incr()`. При `GET` отсутствующего ключа возвращается `redis.Nil` – это нужно обрабатывать.
---
### 1.2. Списки (List)
**Логика:** Упорядоченные коллекции строк, поддерживают вставку/извлечение с обоих концов. Идеальны для очередей (FIFO), стеков (LIFO), логов, брокеров сообщений.  
**Что учить:** LPUSH, RPUSH, LPOP, RPOP, LRANGE, LLEN, LINDEX, BLPOP (блокирующая).  
**Связь с Go:** Методы `LPush`, `RPush`, `LPop`, `RPop`, `LRange`. Для блокирующих очередей – `BLPop` (возвращает `[]string`).
---
### 1.3. Хеши (Hash)
**Логика:** Хеш — это объект, где ключ сопоставляется с набором полей-значений. Удобно хранить профили пользователей, настройки, любые структуры с множеством атрибутов.  
**Что учить:** HSET, HGET, HMSET, HGETALL, HDEL, HEXISTS, HINCRBY, HKEYS, HVALS.  
**Связь с Go:** Методы `HSet`, `HGet`, `HGetAll` (возвращает `map[string]string`), `HDel`, `HIncrBy`.
---
### 1.4. Множества (Set)
**Логика:** Неупорядоченные коллекции уникальных строк. Полезны для тегов, подписчиков, проверки принадлежности, пересечений и объединений.  
**Что учить:** SADD, SREM, SMEMBERS, SISMEMBER, SUNION, SINTER, SDIFF, SCARD.  
**Связь с Go:** `SAdd`, `SRem`, `SMembers` (возвращает `[]string`), `SIsMember`, `SUnion`, `SInter`.
---
### 1.5. Сортированные множества (Sorted Set, ZSET)
**Логика:** Как обычные множества, но каждый элемент связан с числовым «скором», по которому автоматически сортируется. Идеально для рейтингов, лидербордов, очередей с приоритетом, таймеров.  
**Что учить:** ZADD, ZRANK, ZREVRANK, ZRANGE, ZREVRANGE, ZREM, ZSCORE, ZINCRBY, ZCOUNT.  
**Связь с Go:** `ZAdd`, `ZRank`, `ZRange` (возвращает `[]string`), `ZRevRange`, `ZScore`, `ZIncrBy`.

## 🟡 БЛОК 2. УПРАВЛЕНИЕ КЛЮЧАМИ И ВЫТЕСНЕНИЕ
### 2.1. Время жизни (TTL)
**Логика:** Большинство данных в Redis — это кэш, поэтому для каждого ключа полезно устанавливать срок жизни. Это освобождает память автоматически.  
**Что учить:** EXPIRE, PEXPIRE, TTL, PTTL, PERSIST (сделать вечным).  
**Связь с Go:** `Expire`, `TTL`, `Persist`.
### 2.2. Политики вытеснения (Eviction)
**Логика:** Когда память (maxmemory) исчерпана, Redis удаляет ключи по заданному правилу. Выбор политики влияет на доступность данных.  
**Что учить:**
- `noeviction` – ошибка при записи;
- `allkeys-lru` – удаляет редко используемые из всех;
- `volatile-lru` – только среди ключей с TTL;
- `allkeys-random` / `volatile-random`;
- `volatile-ttl` – удаляет с наименьшим оставшимся TTL.  
  Настройка в `redis.conf`: `maxmemory <bytes>` и `maxmemory-policy`.  
- `Maxmemory Overhead & Invalidation`
  **Связь с Go:** В коде это не настраивается, но нужно понимать, какая политика выбрана на сервере, чтобы правильно проектировать кэширование.

## 🟠 БЛОК 3. ПЕРСИСТЕНТНОСТЬ (обязательный вопрос)
### 3.1. RDB (снимки)
**Логика:** Периодически (по условиям) Redis сохраняет полный дамп данных на диск. Быстрое восстановление, компактно, но возможна потеря данных с момента последнего снимка.  
**Что учить:** Настройки `save 900 1`, `save 300 10`; файл `dump.rdb`.  
**Связь с Go:** Приложение не управляет RDB напрямую, но должно быть готово к тому, что при рестарте данные могут быть неактуальными.
### 3.2. AOF (журнал операций)
**Логика:** Каждая команда записывается в журнал. Можно восстановить почти все данные (в зависимости от `appendfsync`). Больше размер, медленнее, но надёжнее.  
**Что учить:** `appendonly yes`, `appendfsync always / everysec / no`, перезапись AOF (BGREWRITEAOF).  
**Связь с Go:** Аналогично – серверная настройка. В коде важно понимать, что AOF может влиять на задержки, особенно при `always`.

## 🔴 БЛОК 4. РЕПЛИКАЦИЯ И ВЫСОКАЯ ДОСТУПНОСТЬ
### 4.1. Master‑Replica (репликация)
**Логика:** Асинхронное копирование данных с мастера на одну или несколько реплик. Повышает пропускную способность для чтения и даёт базовую отказоустойчивость.  
**Что учить:** Настройка `replicaof <masterip> <masterport>`, состояние репликации, возможная задержка, потеря данных при падении мастера.  
**Связь с Go:** go-redis поддерживает чтение с реплик через параметр `ReadOnly` в `NewClusterClient` или при использовании `NewFailoverClient`.
### 4.2. Sentinel
**Логика:** Компонент для мониторинга мастеров и автоматического переключения (failover) на реплику в случае сбоя. Обеспечивает высокую доступность без шардирования.  
**Что учить:** Архитектура Sentinel, конфигурация, клиентское обнаружение.  
**Связь с Go:** Использовать `go-redis/sentinel` – `NewFailoverClient` с параметрами `MasterName`, `SentinelAddrs`. Клиент автоматически переключается на нового мастера.
### 4.3. Redis Cluster
**Логика:** Горизонтальное масштабирование (шардирование) на 16384 слотов. Каждый узел отвечает за свою часть ключей. Обеспечивает и HA, и распределение нагрузки.  
**Что учить:** Слоты, хеширование, редиректы (MOVED/ASK), ограничения (транзакции только в пределах одного слота).  
**Связь с Go:** `go-redis/cluster` – `NewClusterClient` с перечнем адресов узлов. Клиент сам обрабатывает редиректы и маршрутизацию.

## 🟣 БЛОК 5. ТРАНЗАКЦИИ, ПАЙПЛАЙНЫ, LUA
### 5.1. Пайплайн (Pipeline)
**Логика:** Отправка нескольких команд без ожидания ответа между ними, что снижает задержки за счёт уменьшения числа сетевых вызовов. Но атомарность не гарантируется.  
**Что учить:** Команды отправляются пачкой, ответы получают позже.  
**Связь с Go:** `pipe := client.Pipeline()`; затем `pipe.Set(...)`, `pipe.Get(...)`, `cmds, err := pipe.Exec(ctx)`. Ответы разбираются по индексу.
### 5.2. Транзакции (MULTI / EXEC)
**Логика:** Блок команд выполняется атомарно и изолированно от других клиентов. Можно использовать `WATCH` для оптимистической блокировки (CAS).  
**Что учить:** MULTI, EXEC, DISCARD, WATCH, UNWATCH. Ошибки в одной команде не откатывают всю транзакцию.  
**Связь с Go:** `client.TxPipelined(ctx, func(pipe redis.Pipeliner) error { ... })` – это упрощённый синтаксис. Для WATCH – использовать `client.Watch` перед вызовом транзакции.
### 5.3. Lua-скрипты (EVAL)
**Логика:** Сложная логика, которая выполняется атомарно на стороне сервера. Избавляет от гонок и лишних сетевых вызовов.  
**Что учить:** Написание скрипта, передача аргументов, кэширование через `EVALSHA`.  
**Связь с Go:** `client.Eval(ctx, script, keys, args)`; можно использовать `redis.NewScript` для загрузки и многократного вызова.

## 🟤 БЛОК 6. ПРОБЛЕМЫ ПРОИЗВОДИТЕЛЬНОСТИ
### 6.1. KEYS vs SCAN
**Логика:** `KEYS` блокирует сервер на время полного перебора всех ключей – смертельно на продакшне. `SCAN` итеративно возвращает ключи без блокировки.  
**Что учить:** SCAN, SSCAN, HSCAN, ZSCAN – синтаксис, использование курсора.  
**Связь с Go:** `client.Scan(ctx, cursor, match, count)`, итератор `client.Scan(ctx, 0, "", 0).Iterator()`.
### 6.2. Медленные команды и SLOWLOG
**Логика:** Определённые операции (большие LRANGE, ZREMRANGEBYRANK, KEYS) могут тормозить. Мониторинг через `SLOWLOG` помогает найти узкие места.  
**Что учить:** `CONFIG SET slowlog-log-slower-than`, `SLOWLOG GET`, `SLOWLOG LEN`.  
**Связь с Go:** `client.SlowLogGet(ctx, n)` для получения записей.

## 🔵 БЛОК 7. ПАТТЕРНЫ ИСПОЛЬЗОВАНИЯ (архитектурные вопросы)
### 7.1. Кэширование (Cache-Aside)
**Логика:** Сначала читаем из Redis, при промахе – из основной БД и записываем результат в Redis с TTL.  
**Связь с Go:** Реализуется в слое репозитория: `if err := client.Get(ctx, key).Scan(&val); err == nil { return val } else if errors.Is(err, redis.Nil) { ... }`.
### 7.2. Очереди задач
**Логика:** Списки с блокирующими командами (`BLPOP`) или Redis Streams для более надёжной обработки.  
**Связь с Go:** `client.BLPop(ctx, timeout, key)` возвращает первый элемент; для Streams – `XAdd`, `XReadGroup`.
### 7.3. Распределённая блокировка
**Логика:** Простая блокировка через `SET key value NX EX seconds` (атомарно). Для критичных систем – Redlock (но многие критикуют). Изучить Safe Unlock, Auto-refresh.  
**Связь с Go:** `client.SetNX(ctx, key, value, expiration)` – возвращает `bool`.
### 7.4. Rate Limiting
**Логика:** INCR ключа с TTL на период, проверка достижения лимита. Понимать разницу между Fixed Window, Sliding Window и Token Bucket / Leaky Bucket.  
**Связь с Go:** `client.Incr(ctx, key); client.Expire(ctx, key, time.Minute)` и проверка значения.
### 7.5. Лидерборды (рейтинги)
**Логика:** ZADD для добавления очков, ZREVRANGE с LIMIT для топа.  
**Связь с Go:** `client.ZAdd`, `client.ZRevRange(ctx, key, 0, 9)`.
