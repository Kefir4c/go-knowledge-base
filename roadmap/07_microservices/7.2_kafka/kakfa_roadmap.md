# Kafka Roadmap — ПОЛНАЯ ВЕРСИЯ С ДОПОЛНЕНИЯМИ И НЮАНСАМИ

Этот roadmap — минимум, который тебе нужен, чтобы на собеседовании по Kafka выглядеть уверенно на Middle/Middle+ позиции. Дополнительные нюансы по блокам помогут тебе перейти на Senior-уровень.

- Объяснить разницу между at-most-once, at-least-once и exactly-once.
- Понимать, как работают consumer groups и ребалансировка.

- На базовом уровне понимать транзакции и идемпотентность.
- Знать, когда использовать Kafka, а когда — RabbitMQ или NATS.
- Обрабатывать ошибки с DLQ и retry-топиками.
- Понимать, как Partition Key влияет на порядок сообщений.
- Знать паттерн Transactional Outbox для согласованности БД и Кафки.
- Понимать, как Kafka хранит данные на диске (сегменты, индексы, compaction).
- Знать, что такое KRaft и чем он лучше ZooKeeper.

- Понимать метрику Consumer Lag и как её мониторить.

## БЛОК 1: ОСНОВЫ KAFKA
### 1.1. Архитектура Kafka
- Что такое брокер, топик, партиция, продюсер, консюмер.
- Как Kafka хранит данные на диске:
    - Сообщения записываются исключительно in-order (sequential write) в сегментные файлы (.log).
    - Это обеспечивает колоссальную скорость записи (сравнима с RAM).
    - Для поиска по смещению Kafka использует разреженные индексы:
        - .index — для поиска offset → position.
        - .timeindex — для поиска timestamp → offset.
- Роль ZooKeeper/KRaft в управлении кластером:
    - Начиная с версии Kafka 3.3 (и полностью убрано в 4.0), KRaft заменяет ZooKeeper.
    - KRaft работает на основе протокола консенсуса Raft прямо внутри кластера Kafka (Controller nodes).
    - Это убирает внешнюю зависимость и ускоряет мета-операции.

### 1.2. Топики и партиции
- Партиция — единица параллелизма: порядок сообщений гарантируется внутри партиции.
- Смещение (offset) — уникальный идентификатор сообщения в партиции.
- Репликация: leader/follower, ISR (In-Sync Replicas).

### 1.3. Consumer Groups и смещения
- Consumer group — набор консюмеров, совместно читающих топик.
- Правило: одна партиция → один консюмер в группе.
- Смещение (offset) — позиция последнего прочитанного сообщения.
- Автоматический и ручной коммит смещения.

### 1.4. Гарантии доставки (Delivery Semantics)
- At-most-once: сообщение может быть потеряно, но не обработано дважды.
- At-least-once: сообщение не будет потеряно, но может быть обработано повторно (стандарт в Kafka).
- Exactly-once: сообщение обрабатывается ровно один раз (требует идемпотентности и транзакций).

### 1.5. Partition Key и порядок сообщений
- Kafka гарантирует порядок ТОЛЬКО внутри одной партиции.
- Чтобы события одного пользователя обрабатывались строго по порядку, продюсер должен отправлять их с Key = UserID.
- Хэш от ключа определяет номер партиции: partition = hash(key) % number_of_partitions.
- Без ключа (null) сообщения распределяются round-robin — порядок не гарантируется.
- При добавлении новых партиций хэш-функция меняется, и порядок может нарушиться.

## БЛОК 2: ПРОДВИНУТЫЕ ТЕМЫ (MIDDLE+)
### 2.1. Идемпотентный продюсер (enable.idempotence=true)
- Гарантирует отсутствие дублей сообщений в партиции при повторных отправках.
- Каждому продюсеру присваивается уникальный PID.
- Каждому сообщению — порядковый номер в партиции.

### 2.2. Транзакции в Kafka
- Атомарная запись в несколько партиций.
- Связка коммита смещения консюмера с транзакцией продюсера для end-to-end exactly-once.
- Настройка transactional.id и инициализация транзакций.

### 2.3. Exactly-once semantics (EOS)
- Сочетание идемпотентного продюсера + транзакций.
- Consumer с isolation.level=read_committed читает только закоммиченные транзакции.
- Требует согласованной работы продюсера и консюмера.

### 2.4. Обработка ошибок и DLQ (Dead Letter Queue)
- Паттерн DLQ: специальный топик (<original-topic>-dlq) для битых сообщений.
- Retry-топики с задержкой: orders-retry-1s → orders-retry-10s → orders-retry-60s → orders-dlq.
- Блокировка офсета: consumer НЕ коммитит смещение для "отравленного" сообщения.
- Стратегии: DLQ, retry with backoff (экспоненциальная задержка), skip and log.

### 2.5. Transactional Outbox — КРИТИЧЕСКИ ВАЖНО!
- Проблема: сохранение в БД и отправка в Кафку — две разные операции.
- Паттерн Outbox: в ACID-транзакции БД сохраняется запись в таблицу outbox.
- Отдельный воркер (Outbox Publisher) читает из outbox и отправляет в Кафку.
- После успешной отправки запись помечается как обработанная или удаляется.
- Outbox Pattern + Debezium (CDC): самый чистый вариант — Debezium парсит WAL PostgreSQL и сам гарантирует отправку at-least-once без дополнительных воркеров.
- Если писать воркер руками: важно использовать SELECT ... FOR UPDATE SKIP LOCKED, чтобы несколько реплик не вычитывали одни и те же записи.

## БЛОК 3: БИБЛИОТЕКИ ДЛЯ GO
### 3.1. confluent-kafka-go
- Официальный клиент от Confluent, основан на librdkafka (CGO).
- Высокая производительность, поддержка всех фич (транзакции, EOS).
- Единственный выбор для проектов, где критична 100% совместимость с enterprise-фичами Kafka / Confluent Cloud и предельная производительность.
- Минус: зависимость от CGO, нет поддержки Go context.

### 3.2. segmentio/kafka-go
- Чистый Go, без CGO — легче устанавливать.
- Простой API, хорошо подходит для асинхронных сценариев.
- Минус: нет поддержки транзакций, производительность ниже.

### 3.3. IBM/sarama
- Разработан Shopify, сейчас поддерживается IBM.
- Чистый Go, без CGO — лёгкая установка.
- Поддерживается enterprise-проектами и legacy-системами.
- Поддерживает транзакции и идемпотентность (в отличие от segmentio/kafka-go).
- Имеет низкоуровневый и высокоуровневый API (sarama и sarama-cluster).

### 3.4. Какую выбирать?
- confluent-kafka-go: максимальная производительность, поддержка EOS, high-load (CGO).
- sarama: чистый Go с EOS и enterprise-поддержкой (IBM).
- segmentio/kafka-go: простота, без EOS, Pure Go.

## БЛОК 4: SENIOR-ТЕМЫ (ДЛЯ ЖИРНОГО ПЛЮСА)
### 4.1. Acks (Подтверждения от продюсера) — ДОБАВЛЕНО
- acks=0: Продюсер не ждет ответа (максимальная скорость, минимальная надежность).
- acks=1: Продюсер ждет записи только на Leader-реплику.
- acks=all (-1): Продюсер ждет записи от всех текущих ISR (в связке с min.insync.replicas).

### 4.2. Consumer Rebalance
- Когда происходит: добавление/удаление консюмера, изменение подписки.
- Стратегии:
    - Range, RoundRobin, Sticky (старые).
    - Cooperative (Incremental Cooperative Rebalancing): в отличие от Eager Rebalance (stop-the-world), позволяет переназначать только те партиции, которые реально меняют владельца, не останавливая работу остальной группы.
- Static Membership (group.instance.id) для уменьшения ребалансировок.

### 4.3. ISR (In-Sync Replicas) и min.insync.replicas
- ISR — реплики, синхронизированные с лидером.
- min.insync.replicas — минимальное количество реплик в ISR для подтверждения записи.
- Сочетание с acks=all: продюсер ждёт подтверждения от всех реплик в ISR.
- Влияние на надёжность и доступность.

### 4.4. Monitoring and Metrics
- Consumer Lag: разница между последним смещением в партиции (Log End Offset) и текущим закоммиченным офсетом группы (Current Offset). Главный показатель здоровья консюмера.
- Другие метрики: under-replicated partitions, ISR shrink/expand.
- Инструменты: Kafka Manager, Burrow, Prometheus + JMX exporter.

## БЛОК 5: ОЗНАКОМИТЕЛЬНО — RABBITMQ И NATS
### 5.1. RabbitMQ
- Протокол AMQP, классический брокер.
- Концепции: exchange, queue, routing key, binding.
- Поддержка сложной маршрутизации и различных протоколов (MQTT, STOMP).
- Библиотека для Go: amqp091-go.

### 5.2. NATS
- Лёгкий, высокопроизводительный брокер.
- Концепции: subject, JetStream (persistence и replay).
- Используется в микросервисах, IoT, low-latency системах.
- Библиотека для Go: nats.go.

### 5.3. Когда что использовать?
- Kafka: большие объёмы данных, долгосрочное хранение, streaming, exactly-once.
- RabbitMQ: сложная маршрутизация, разнородные протоколы, устаревшие системы.
- NATS: лёгкость, низкая задержка, облачные/IoT системы.

## БЛОК 6: ПРАКТИКА (ЧТО НАПИСАТЬ В ПРИМЕРЕ)
- Producer:
    - Стандартная отправка (at-least-once) с разными acks.
    - Идемпотентный продюсер.
    - Транзакции.
- Consumer:
    - Чтение в цикле с ручным коммитом.
    - Обработка ошибок и переподключение.
    - DLQ при битых сообщениях.
    - Retry с задержкой.
- Consumer Group:
    - Два консюмера в одной группе для параллельной обработки.
- Использование библиотеки segmentio/kafka-go (или confluent/sarama) с комментариями.

## КЛЮЧЕВЫЕ ВЫВОДЫ
1. Kafka — распределённый брокер сообщений с хранением на диске.
2. Партиция — единица параллелизма: одна партиция → один consumer в группе.
3. Consumer Group — набор потребителей, совместно читающих топик.
4. At-least-once — стандарт в Kafka: сообщение не теряется, но может дублироваться.
5. Exactly-once — достигается через идемпотентный продюсер + транзакции.
6. Идемпотентный продюсер — гарантирует отсутствие дублей в партиции.
7. Транзакции — атомарная запись в несколько партиций.
8. confluent-kafka-go — для высокой производительности и EOS (CGO).
9. sarama — чистый Go с EOS и enterprise-поддержкой (IBM).
10. segmentio/kafka-go — для простоты без EOS (Pure Go).
11. Senior-темы: rebalance strategies, ISR, min.insync.replicas, acks, Cooperative Rebalance, Consumer Lag.
12. Kafka — для больших потоков данных, RabbitMQ — для сложной маршрутизации,
    NATS — для лёгкости и скорости.
13. DLQ (Dead Letter Queue) — обязательный паттерн для обработки битых сообщений.
14. Partition Key — определяет порядок: события с одним ключом попадают
    в одну партицию.
15. Transactional Outbox — гарантирует, что данные не потеряются при сбое
    между БД и Кафкой.
16. Kafka хранит данные как sequential write, использует разреженные индексы.
17. KRaft заменяет ZooKeeper начиная с Kafka 3.3.
18. Всегда учитывай гарантии доставки и настраивай consumer'ов с учётом
    обработки ошибок (DLQ, retry, блокировка офсета).
